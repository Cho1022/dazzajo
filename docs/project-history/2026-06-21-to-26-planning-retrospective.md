## 06월 21일 — 문제 정의와 MVP 경계 설정

### 목표

PC 부품 추천 서비스가 해결해야 할 문제를 “상품 목록 제공”이 아니라 “사용자 조건을 근거와 함께 검증 가능한 견적으로 전환하는 일”로 정의했다. 추천 결과만 보여 주는 챗봇은 호환성, 소비전력, 규격, 가격의 책임 주체가 불분명하므로 MVP의 중심에서 제외했다.

### 핵심 결정

- 입력은 예산, 용도, 우선순위, 브랜드 선호를 포함한 자연어로 받는다.
- 출력은 단일 정답이 아니라 비교 가능한 추천 Build와 경고, 근거를 제공한다.
- LLM은 요구사항 해석과 설명을 담당하고, 호환성·전력·규격·성능 범위·가격 판정은 검증 Tool이 담당한다.
- 결제, 배송, 자체 원격제어, 정확한 FPS 및 최저가 보장은 MVP 범위에서 제외한다.

### 업무 산출물과 완료 기준

첫날의 산출물은 기능 목록이 아니라 제품 원칙이었다. 이후 모든 기능은 `자연어 입력 → 근거 검색 → 규칙 검증 → 추천 및 경고` 흐름을 강화하는지로 우선순위를 판단한다. 완료 기준은 사용자에게 추천 이유와 경고 근거를 설명할 수 있고, 관리자가 같은 실행의 Agent·RAG·Tool 기록을 추적할 수 있는 상태로 정했다.

### 리스크와 다음 결정

가장 큰 리스크는 “AI 추천”이라는 표현이 검증 책임까지 LLM에 위임하는 것으로 오해되는 점이었다. 다음 날에는 사용자 여정과 운영자 여정을 하나의 E2E 흐름으로 연결해 제품 범위를 화면 단위로 고정하기로 했다.

## 06월 22일 — 사용자·운영자 E2E 흐름 고정

### 목표

전날 정한 제품 원칙을 실제 사용 장면으로 바꿨다. 사용자가 자연어로 요구사항을 남긴 순간부터 추천 결과를 비교하고, 부품을 변경하고, 사후 지원까지 이어지는 하나의 여정을 기준으로 화면과 API 후보를 정리했다.

### 핵심 결정

사용자 흐름은 `요구사항 입력 → RAG 근거 검색 → Build 후보 생성 → Tool 검증 → 추천 결과 → 부품 변경 비교 → 가격 알림` 순서로 고정했다. 장애나 성능 저하가 발생한 뒤에는 PC Agent가 최근 30분의 JSONL 로그를 만들고, 사용자의 명시적 동의 후 AS 티켓에 연결하도록 했다. 사용자 화면에는 티켓 번호와 처리 상태만 제공하고, 원인 후보·근거·Tool 호출 내역은 관리자 화면에서만 확인하도록 정보 경계를 분리했다.

### 업무 산출물과 완료 기준

화면은 견적/추천, 부품/가격, 인증, 지원, 관리자 영역으로 나눴다. 각 화면은 독립된 데모가 아니라 같은 식별자를 전달하는 연속 흐름이어야 한다. 추천 결과의 Build ID가 부품 변경과 저장으로 이어지고, 로그 업로드 ID가 AS 티켓과 Agent 분석 기록으로 이어지는 것을 E2E 완료 기준으로 삼았다.

### 리스크와 다음 결정

화면 수만 늘리면 데모는 가능해도 데이터 추적성이 깨질 수 있었다. 다음 날에는 추천 단계별 책임을 LLM·RAG·Tool로 분리하고 모든 검증 결과가 같은 공통 형식으로 남도록 계약을 먼저 정의하기로 했다.
