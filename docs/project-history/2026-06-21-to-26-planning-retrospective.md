이 문서는 다짜조(BuildGraph AI 프로토타입)가 단순 아이디어에서 5인 병렬 개발이 가능한 실행 계획으로 구체화되는 과정을 하루 단위로 정리한 기획 회고다. 신규 합류자와 리뷰어가 “무엇을 만들었는가”보다 “어떤 문제를 어떤 순서로 좁혔는가”를 빠르게 파악하는 것을 목표로 한다.

## 06월 21일 — 문제 정의와 MVP 경계 설정

### 목표

PC 부품 추천 서비스가 해결해야 할 문제를 “상품 목록 제공”이 아니라 “사용자 조건을 근거와 함께 검증 가능한 견적으로 전환하는 일”로 정의했다. 추천 결과만 보여 주는 챗봇은 호환성, 소비전력, 규격, 가격의 책임 주체가 불분명하므로 MVP의 중심에서 제외했다.

### 핵심 결정

- 입력은 예산, 용도, 우선순위, 브랜드 선호를 포함한 자연어로 받는다.
- 출력은 단일 정답이 아니라 비교 가능한 추천 Build와 경고, 근거를 제공한다.
- LLM은 요구사항 해석과 설명을 담당하고, 호환성·전력·규격·성능 범위·가격 판정은 검증 Tool이 담당한다.
- 결제, 배송, 자체 원격제어, 정확한 FPS 및 최저가 보장은 MVP 범위에서 제외한다.

### 업무 산출물과 완료 기준

첫날의 산출물은 기능 목록이 아니라 제품 원칙이었다. 이후 모든 기능은 `자연어 입력 → 근거 검색 → 규칙 검증 → 추천 및 경고` 흐름을 강화하는지로 우선순위를 판단한다. 완료 기준은 사용자에게 추천 이유와 경고 근거를 설명할 수 있고, 관리자가 같은 실행의 Agent·RAG·Tool 기록을 추적할 수 있는 상태로 정했다.

### 리스크와 다음 결정

가장 큰 리스크는 “AI 추천”이라는 표현이 검증 책임까지 LLM에 위임하는 것으로 오해되는 점이었다. 다음 날에는 사용자 여정과 운영자 여정을 하나의 E2E 흐름으로 연결해 제품 범위를 화면 단위로 고정하기로 했다.

## 06월 22일 — 사용자·운영자 E2E 흐름 고정

### 목표

전날 정한 제품 원칙을 실제 사용 장면으로 바꿨다. 사용자가 자연어로 요구사항을 남긴 순간부터 추천 결과를 비교하고, 부품을 변경하고, 사후 지원까지 이어지는 하나의 여정을 기준으로 화면과 API 후보를 정리했다.

### 핵심 결정

사용자 흐름은 `요구사항 입력 → RAG 근거 검색 → Build 후보 생성 → Tool 검증 → 추천 결과 → 부품 변경 비교 → 가격 알림` 순서로 고정했다. 장애나 성능 저하가 발생한 뒤에는 PC Agent가 최근 30분의 JSONL 로그를 만들고, 사용자의 명시적 동의 후 AS 티켓에 연결하도록 했다. 사용자 화면에는 티켓 번호와 처리 상태만 제공하고, 원인 후보·근거·Tool 호출 내역은 관리자 화면에서만 확인하도록 정보 경계를 분리했다.

### 업무 산출물과 완료 기준

화면은 견적/추천, 부품/가격, 인증, 지원, 관리자 영역으로 나눴다. 각 화면은 독립된 데모가 아니라 같은 식별자를 전달하는 연속 흐름이어야 한다. 추천 결과의 Build ID가 부품 변경과 저장으로 이어지고, 로그 업로드 ID가 AS 티켓과 Agent 분석 기록으로 이어지는 것을 E2E 완료 기준으로 삼았다.

### 리스크와 다음 결정

화면 수만 늘리면 데모는 가능해도 데이터 추적성이 깨질 수 있었다. 다음 날에는 추천 단계별 책임을 LLM·RAG·Tool로 분리하고 모든 검증 결과가 같은 공통 형식으로 남도록 계약을 먼저 정의하기로 했다.

## 06월 23일 — AI·RAG·Tool 책임 경계 설계

### 목표

추천 품질을 모델의 말솜씨가 아니라 재현 가능한 실행 과정으로 관리하도록 AI 계층의 책임을 분리했다. Agent는 무제한 자율 실행기가 아니라 정해진 순서와 비용 정책 안에서 RAG와 Tool을 호출하는 제한된 오케스트레이터로 정의했다.

### 핵심 결정

- LLM: 자연어 요구사항 파싱, 추가 질문, 추천 및 부품 변경 영향 설명, 얕은 AS 원인 후보 생성
- RAG: 부품 사양과 검증 규칙의 출처를 검색하고 추천 결과에 근거 ID 연결
- Tool: `compatibility`, `power`, `size`, `performance`, `price`의 최종 판정
- 실행 순서: `RAG 검색 → Build 후보 → 호환성/전력/규격 → 성능 범위/병목 → 가격 → 종합 설명`

Tool 응답은 `status(PASS/WARN/FAIL)`, `score`, `confidence(LOW/MEDIUM/HIGH)`, `summary`, `warnings`, `evidence`를 공통 필드로 갖도록 했다. 이렇게 하면 프론트는 Tool마다 다른 결과 구조를 해석하지 않아도 되고, 관리자는 어떤 근거로 경고가 발생했는지 같은 방식으로 검토할 수 있다.

### 업무 산출물과 완료 기준

공통 Tool 경로는 `POST /api/tools/{tool}/check`로 축약하고, 추천 한 건마다 Agent session, RAG evidence, Tool invocation이 연결되도록 추적 단위를 잡았다. 외부 호출이 실패하더라도 안전한 대체 추천이 가능하면 경고와 fallback 이력을 남기는 것을 완료 기준으로 정했다.

### 리스크와 다음 결정

책임을 분리해도 API와 데이터 이름이 다르면 병렬 구현에서 다시 결합 비용이 발생한다. 다음 날에는 public ID, 상태 전이, 저장 트랜잭션, 로그 보관 정책을 API·DB 계약으로 동결하기로 했다.

## 06월 24일 — API·DB 계약과 추적성 고정

### 목표

5명이 동시에 프론트엔드와 백엔드를 구현해도 요청·응답과 저장 구조가 어긋나지 않도록 사람용 계약과 기계 검증 기준을 먼저 세웠다. 화면 구현보다 API path, 식별자, 상태값, 소유 테이블을 먼저 동결하는 방식으로 협업 순서를 바꿨다.

### 핵심 결정

외부 API의 모든 `id`와 `*Id`는 내부 BIGINT PK가 아닌 `public_id` 문자열로 통일했다. Agent 실행은 `QUEUED → RUNNING → RAG_SEARCHED → TOOLS_CALLED → SUMMARY_READY → SUCCEEDED`를 정상 흐름으로 두고, 복구 가능한 실패는 `FALLBACK_READY` 이력과 경고를 남기도록 했다. 추천 계산은 DB 트랜잭션 밖에서 수행하되, 최종 Build·item·Agent session·RAG evidence·Tool invocation 저장은 하나의 트랜잭션으로 묶어 응답에 미완성 추적 데이터가 노출되지 않게 했다.

PC Agent 로그는 한 줄에 하나의 관측치를 갖는 JSON Lines로 정했다. AS 요청 시 최근 30분만 명시적 동의 후 업로드하고, `delete_after`를 기준으로 30일 뒤 삭제하는 보관 정책을 데이터 계약에 포함했다.

### 업무 산출물과 완료 기준

사람이 합의할 기준은 `API_CONTRACT.md`, `DB_SCHEMA.md`, `ROUTE_OWNERSHIP.md`로 분리하고, `openapi.yaml`을 프론트·백엔드 요청 구조의 기계 검증 기준으로 뒀다. API 변경 PR은 OpenAPI를, DB 상태·컬럼 변경 PR은 DB 계약을 같은 변경에서 수정해야 완료된 것으로 본다.

### 리스크와 다음 결정

계약이 명확해도 공유 파일과 교차 도메인 쓰기 권한이 모호하면 충돌이 반복된다. 다음 날에는 5명의 담당 영역과 리뷰가 필요한 공유 지점을 route, package, table 단위로 고정하기로 했다.

## 06월 25일 — 5인 병렬 개발 구조와 소유권 확정

### 목표

기능을 프론트/백엔드 직군으로만 나누지 않고, 한 명이 자신의 화면·API·DB·테스트를 끝까지 책임지는 도메인 단위로 재편했다. 동시에 공통 인프라 담당자가 전체 백엔드의 병목이 되지 않도록 직접 수정 영역과 리뷰 영역을 구분했다.

### 담당 구조

| 담당 | 주 책임 | 주요 연결 지점 |
| --- | --- | --- |
| 1번 | 견적·추천·인증 화면 | requirements, builds, build items |
| 2번 | 부품·가격·검증 Tool | parts, price, compatibility, benchmark |
| 3번 | Agent·RAG·근거 추적 | sessions, invocations, evidence |
| 4번 | PC Agent·로그·AS | log uploads, tickets, support UI |
| 5번 | 공통 인증·관리자 shell·인프라·CI | security, shared API client, migration order |

### 핵심 결정

새 구현은 담당 feature/domain 안에 두고, 공통 barrel 파일에는 구현을 쌓지 않도록 했다. 다른 담당 테이블은 기본적으로 읽기만 허용하며 쓰기가 필요하면 owner와 API/DTO를 먼저 맞춘다. `AdminShell`, 공통 UI, 인증 헤더, 오류 정규화, Flyway 순서처럼 영향 범위가 큰 지점은 주 owner와 필수 리뷰어를 별도로 지정했다.

### 업무 산출물과 완료 기준

PR 설명에는 변경한 route, API, DB table, owner를 적고, 담당별 smoke test에서 정상 응답뿐 아니라 401/403, 본인 소유가 아닌 자원 404, 금지 상태 전이 409까지 확인하도록 했다. 완료는 “코드가 동작함”이 아니라 “담당 경계를 침범하지 않고 계약 테스트를 통과함”으로 정의했다.

### 리스크와 다음 결정

소유권 표만으로는 개발 환경 차이와 통합 시점을 해결할 수 없다. 마지막 날에는 한 명이 새 PC에서 같은 환경을 재현하고, PR 단계에서 계약·빌드·런타임을 자동 검증하는 실행 기반을 정리하기로 했다.

## 06월 26일 — 스캐폴드·검증 기준·팀 인계 준비

### 목표

기획을 발표 자료에 머물게 하지 않고 다음 날부터 바로 구현할 수 있는 저장소 구조로 번역했다. 공통 환경을 먼저 고정하고, 각 담당자가 자신의 feature/domain에서 독립적으로 첫 PR을 낼 수 있는 시작점을 정의했다.

### 핵심 결정

모노레포는 React/Vite 웹, Spring Boot API, Python PC Agent, Docker 인프라로 구성하고 PostgreSQL+pgvector, Redis, RabbitMQ, Mailpit을 Compose 한 번으로 실행하도록 계획했다. API는 도메인 controller 골격과 seed 응답에서 시작하되, 계약을 유지하며 DTO/service/repository와 실제 DB 연결로 단계적으로 교체하도록 했다.

CI는 웹 build와 route smoke test, API `bootJar`, OpenAPI 검증, Docker Compose 구성 검사, DB 연결을 포함한 `/api/health` runtime smoke를 PR의 공통 게이트로 삼았다. 1주차에는 계약과 담당별 happy path를 고정하고, 3주차에는 자연어 입력부터 추천·부품 변경·가격 알림·로그 업로드·AS 티켓·관리자 근거 확인까지 전체 E2E를 연결하는 목표를 세웠다.

### 업무 산출물과 완료 기준

- 새 팀원이 README 순서대로 문서를 읽고 `docker compose up --build`로 같은 환경을 실행할 수 있다.
- 기능 담당자는 `ROUTE_OWNERSHIP.md`에서 자신의 route, API, DB table, 리뷰어를 찾을 수 있다.
- 요청/응답 변경은 OpenAPI 검증으로, 상태·보관 정책 변경은 DB 계약 검토로 확인할 수 있다.
- PC Agent 샘플 생성과 최근 30분 export가 AS 업로드 시나리오의 고정 fixture로 동작한다.

### 남은 리스크와 인계

실제 LLM/RAG 품질, 정교한 Tool 규칙, 센서 수집, 300/1,000명 부하는 스캐폴드 단계의 완료 항목이 아니다. 첫 구현에서는 seed 기반 happy path를 깨지 않으면서 각 도메인의 실제 연결을 교체하고, 계약에 없는 API·상태·컬럼이 필요하면 구현 전에 팀 합의를 거치도록 인계했다. 이 준비는 6월 27일 최초 스캐폴드 커밋 `4f0a1ffa`와 후속 협업 기준 문서로 구체화됐다.
